[이슈 #1] 포트 8000 충돌 — 다른 프로세스가 점유
----------------------------------------------------

▶ 발생 시점
  Phase 3 로컬 테스트 중. 프론트에서 영상 업로드 시 아래 오류 발생.

▶ 증상
  1차: [vite] http proxy error: /api/upload — Error: read ECONNRESET
  2차: Failed to load resource: the server responded with a status of 404 (Not Found)

▶ 원인 분석

  1차 오류 (ECONNRESET):
    백엔드 서버가 아예 실행되지 않은 상태에서 프론트엔드만 실행됨.
    Vite 프록시가 localhost:8000으로 요청을 보냈지만 아무도 없어서
    연결 자체가 끊김 (Connection Reset).

  2차 오류 (404):
    uvicorn을 실행했는데 http://localhost:8000/docs에 접속하면
    analog 프로젝트의 API 목록이 표시됨.
    → 이전에 실행된 analog 서버 프로세스들이 포트 8000을 점유 중.

  netstat 확인 결과:
    TCP  0.0.0.0:8000   LISTENING  33488  ← 우리 uvicorn (reloader)
    TCP  127.0.0.1:8000 LISTENING  27480  ← analog 서버
    TCP  127.0.0.1:8000 LISTENING  31768  ← analog 서버
    TCP  127.0.0.1:8000 LISTENING  23220  ← analog 서버

  Windows에서 동일 포트에 여러 프로세스가 바인딩 가능한 이유:
    SO_REUSEADDR 옵션 때문. 연결 요청이 오면 OS가 임의로
    하나에 전달하는데, analog 서버로 먼저 라우팅됨.

  taskkill로 제거 시도했지만 실패한 이유:
    해당 프로세스들이 WSL(Windows Subsystem for Linux) 내부에서
    실행 중이었음. Windows의 netstat에는 보이지만 Windows PID로
    kill 불가. WSL 내부에서 kill하거나 wsl --shutdown 필요.

▶ 해결 방법

  방법 1 (즉각 해결): 포트 변경
    - 백엔드를 8001 포트로 실행
        uvicorn main:app --reload --host 0.0.0.0 --port 8001
    - vite.config.js 프록시 타겟 변경
        '/api': 'http://localhost:8001'
    → 채택. 단순하고 빠름.

  방법 2 (근본 해결): WSL에서 프로세스 종료
    WSL 터미널에서:
        fuser -k 8000/tcp
    또는 WSL 전체 재시작:
        wsl --shutdown  (PowerShell 관리자 권한)

▶ 교훈
  - 서버 개발 시 포트 충돌은 흔한 이슈. 항상 netstat으로 확인 습관 필요.
  - WSL + Windows 혼용 환경에서는 프로세스 관리 주체가 달라
    Windows에서 kill이 안 되는 케이스 발생 가능.
  - 개발 환경에서 포트 번호를 팀/프로젝트별로 정해두면 충돌 예방 가능.
    (예: analog=8000, webpage=8001, 다른 프로젝트=8002)

[이슈 #2] UniMatch CONF_THRESH=0.95 → Unsupervised loss 완전 무력화
----------------------------------------------------

▶ 발생 시점
  train_lora_unimatch.py 학습 중 PyCharm 디버거로 confidence 값 확인.

▶ 증상
  모든 배치에서 conf threshold 통과 픽셀 = 0/262144 (0.0%)
  conf 평균 = 0.008~0.015 수준

▶ 원인 분석
  - Teacher 모델 = Student 복사본으로 시작 → 학습 초반엔 둘 다 미학습 상태
  - 미학습 모델의 sigmoid 출력이 0에 가까움 (logit ≈ -5 → sigmoid ≈ 0.007)
  - CONF_THRESH = 0.95를 통과하는 픽셀이 없음 → pseudo-label 전부 비어있음
  - loss_unsup = 0 → Semi-supervised가 아닌 Supervised only 학습과 동일

  sigmoid(x) ≈ 0.95 를 만족하려면 logit x ≈ +2.94 이상이어야 함.
  학습 초반 모델 출력 logit ≈ -5 → 한참 부족.

▶ 해결 방법
  학습을 반복하니까 conf가 올라가서 해결됨.
  conf를 낮춰서 학습을 진행하면 pseudo-label의 quality가 낮아져서 오히려 모델 성능 감소
  학습 초만에 warmup 추가
▶ 교훈
  - Semi-supervised 학습에서 confidence threshold는 모델 성숙도에 맞게 설정해야 함.
  - 학습 초반 teacher 신뢰도가 낮으므로 threshold를 낮춰가면서 적정 threshold를 찾아야함.
  - 디버거로 실제 confidence 분포를 확인하는 것이 hyperparameter 결정에 필수적.
  - 고급 전략: threshold를 epoch에 따라 점진적으로 높이는 curriculum 방식도 가능.

[이슈 #3] AWS EC2 배포 — 영상 업로드 413 오류
----------------------------------------------------

▶ 발생 시점
  Phase 5 AWS EC2 배포 후 브라우저에서 영상 업로드 시 발생.

▶ 증상
  브라우저 F12 콘솔:
    Failed to load resource: the server responded with a status of 413 (Request Entity Too Large)

▶ 원인 분석
  nginx 기본 설정의 client_max_body_size = 1MB.
  영상 파일이 이를 초과하여 nginx 단에서 요청 자체를 거부.

▶ 해결 방법
  /etc/nginx/sites-available/default 에 아래 추가:
    server {
        client_max_body_size 500M;
        ...
    }

  적용 명령어:
    sudo nginx -t
    sudo systemctl restart nginx

▶ 교훈
  - nginx는 FastAPI 앞단에서 요청을 먼저 처리하므로
    파일 업로드 관련 제한은 nginx 설정에서도 반드시 확인해야 함.
  - nginx 설정 변경 후 항상 nginx -t 로 문법 검사 후 재시작.

[이슈 #4] EC2 배포 — OpenCV 코덱 미지원으로 프레임 추출 실패
----------------------------------------------------

▶ 발생 시점
  EC2에서 영상 업로드 후 추론 시작 시 오류 발생.

▶ 증상
  [Job xxxxx] 오류: no images found in /tmp/smas_web_xxxxxx

▶ 원인 분석
  로컬 inference.py의 extract_frames 함수가 OpenCV(cv2.VideoCapture)로
  프레임을 추출하는 방식이었음.
  EC2 Ubuntu에서 opencv-python-headless는 mp4 코덱(H.264 등) 지원이
  기본 포함되어 있지 않아 cap.read()가 프레임을 읽지 못함.
  → 추출된 프레임 0개 → "no images found" 에러

  확인 명령어:
    sudo journalctl -u beauty -n 50 --no-pager

▶ 해결 방법
  extract_frames 함수를 OpenCV 대신 ffmpeg subprocess 방식으로 교체.
  - fps/해상도: ffprobe로 추출
  - 프레임: ffmpeg으로 PNG 추출

  변경된 코드:
    probe_cmd = ["/usr/bin/ffprobe", "-v", "error", ...]
    cmd = ["/usr/bin/ffmpeg", "-y", "-i", video_path, "frame_%05d.png"]

  systemd 환경에서는 PATH가 제한되므로 ffmpeg/ffprobe 절대경로 사용:
    which ffmpeg  →  /usr/bin/ffmpeg
    which ffprobe →  /usr/bin/ffprobe

  적용 명령어 (로컬 → EC2 전송):
    scp -i beauty-key.pem inference.py ubuntu@<IP>:~/beauty/webpage/backend/
    sudo systemctl restart beauty

▶ 교훈
  - 로컬(Windows)과 서버(Linux) 환경의 코덱 지원 차이를 항상 고려해야 함.
  - systemd 서비스는 PATH가 /usr/bin 등으로 제한되어 which로 확인한
    절대경로를 사용해야 안전함.
  - subprocess 호출 시 stderr=DEVNULL 이면 에러가 숨겨지므로
    디버깅 시 capture_output=True 로 변경하여 에러 내용 확인 필요.

[이슈 #5] EC2 배포 — MedSAM2 구버전이 PNG 미지원
----------------------------------------------------

▶ 발생 시점
  이슈 #4 해결 후에도 동일한 "no images found" 오류 지속.

▶ 증상
  watch -n 1 'ls /tmp/smas_web_*' 로 모니터링하니
  프레임 PNG 파일들은 정상 생성됨.
  그럼에도 "no images found" 에러 발생.

▶ 원인 분석
  EC2에 클론한 MedSAM2(bowang-lab/MedSAM2)는 구버전으로
  sam2/utils/misc.py의 load_video_frames_from_jpg_images 함수가
  .jpg/.jpeg 확장자만 인식:

    if os.path.splitext(p)[-1] in [".jpg", ".jpeg", ".JPG", ".JPEG"]  ← PNG 없음

  로컬 MedSAM2는 .png/.PNG 도 포함된 버전이었으나
  EC2에 git clone 한 버전은 이전 커밋 기준으로 PNG 지원 없음.

  확인 명령어:
    grep -n "png\|jpg\|images found" ~/beauty/MedSAM2/sam2/utils/misc.py

▶ 해결 방법
  방법 1 (채택): EC2의 misc.py에 PNG 확장자 직접 추가
    sed -i 's/in \[".jpg", ".jpeg", ".JPG", ".JPEG"\]/in [".jpg", ".jpeg", ".JPG", ".JPEG", ".png", ".PNG"]/' \
      ~/beauty/MedSAM2/sam2/utils/misc.py

  방법 2 (대안): ffmpeg 추출 시 jpg로 저장
    frame_%05d.png → frame_%05d.jpg 로 변경

  sudo systemctl restart beauty

▶ 교훈
  - EC2에 git clone 할 때 로컬과 동일한 커밋/버전인지 확인 필요.
  - 외부 라이브러리의 파일 포맷 지원 범위를 미리 파악해야 함.
  - 문제 재현을 위해 watch, journalctl 등 모니터링 도구를 적극 활용.
    watch -n 1 'ls /tmp/smas_web_*'  ← 파일 생성 여부 실시간 확인
    sudo journalctl -u beauty -f     ← 서비스 로그 실시간 확인

====================================================
● EC2 로그 확인 명령어 정리
---                                                                                                                                                                                                                                 1. sudo journalctl -u beauty -n 50 --no-pager

journalctl          → systemd가 수집한 모든 로그를 보는 명령어
-u beauty           → beauty.service 유닛만 필터링 (u = unit)
-n 50               → 최근 50줄만 출력 (n = number)
--no-pager          → less처럼 스크롤 없이 터미널에 바로 출력

---
2. sudo journalctl -u beauty -f

-f                  → follow 모드. 실시간으로 새 로그가 찍히면 바로 출력
                    (tail -f 와 동일한 개념)
                    Ctrl+C 로 종료

---
3. sudo journalctl -u beauty -n 30 --no-pager | grep -A 20 "ERROR\|error\|Traceback"

| grep              → 파이프. 앞 명령어 출력을 grep으로 넘김
"ERROR\|error\|..."  → ERROR 또는 error 또는 Traceback 이 포함된 줄 검색
                     \| 는 OR 조건
-A 20               → 매칭된 줄 이후 20줄도 함께 출력 (A = After)
                     에러 메시지 이후 traceback 전체를 보기 위함

---
4. watch -n 1 'ls /tmp/smas_web_* 2>/dev/null'

watch               → 명령어를 주기적으로 반복 실행하며 화면 갱신
-n 1                → 1초마다 반복
'ls /tmp/smas_web_*' → /tmp 안에 smas_web_ 로 시작하는 파일/폴더 목록 출력
2>/dev/null         → 에러 출력(stderr)을 /dev/null로 버림
                    → 폴더 없을 때 "No such file" 에러 메시지 숨김

---
5. grep -n "png\|jpg\|images found" ~/beauty/MedSAM2/sam2/utils/misc.py

grep                → 파일에서 패턴 검색
-n                  → 매칭된 줄의 줄번호 출력
"png\|jpg\|..."     → png 또는 jpg 또는 images found 포함된 줄
~/beauty/...        → 검색 대상 파일 경로

---
6. sudo systemctl status beauty

systemctl           → systemd 서비스 관리 명령어
status beauty       → beauty.service 의 현재 상태 확인
                    Active: active (running) → 정상
                    Active: failed           → 죽어있음
                    최근 로그 일부도 함께 출력됨
